Campus Connect: Shared Backend and Database Plan

Implementation guide for the Campus Connect website and native Android application

Objective: make the PHP website and Android app use the same accounts, listings, messages, verification state, and marketplace data through one API and one hosted database.

1. Target Architecture

Website JavaScript  ----\
                       PHP REST API ---- MySQL or MariaDB
Android Retrofit   ----/

Android SQLite/Room: local cache only, not the authoritative database

The website currently stores accounts in users.json. The Android app currently stores users and posts in local SQLite. Replace both as the source of truth with a server-side database. Android may retain Room or SQLite for offline caching after the API is working.

2. Recommended Technology

  • Backend: PHP 8.2+ using PDO and JSON API responses.
  • Database: MySQL or MariaDB on a hosted server.
  • Website: JavaScript fetch() calls to the API.
  • Android: Retrofit and OkHttp.
  • Authentication: HTTPS, hashed passwords, email verification, access tokens, and refresh tokens.

3. Core Database Schema

CREATE TABLE users (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    username VARCHAR(30) NOT NULL UNIQUE,
    email VARCHAR(255) NOT NULL UNIQUE,
    password_hash VARCHAR(255) NOT NULL,
    campus VARCHAR(120) NOT NULL,
    is_verified BOOLEAN NOT NULL DEFAULT FALSE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE verification_tokens (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    user_id BIGINT UNSIGNED NOT NULL,
    token_hash VARCHAR(255) NOT NULL,
    expires_at DATETIME NOT NULL,
    used_at DATETIME NULL,
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);

CREATE TABLE listings (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    user_id BIGINT UNSIGNED NOT NULL,
    title VARCHAR(160) NOT NULL,
    description TEXT NOT NULL,
    category VARCHAR(50) NOT NULL,
    price DECIMAL(10,2) NULL,
    campus VARCHAR(120) NOT NULL,
    status ENUM('active','reserved','sold','removed') DEFAULT 'active',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);

CREATE TABLE conversations (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    listing_id BIGINT UNSIGNED NULL,
    buyer_id BIGINT UNSIGNED NOT NULL,
    seller_id BIGINT UNSIGNED NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (listing_id) REFERENCES listings(id) ON DELETE SET NULL,
    FOREIGN KEY (buyer_id) REFERENCES users(id),
    FOREIGN KEY (seller_id) REFERENCES users(id)
);

CREATE TABLE messages (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    conversation_id BIGINT UNSIGNED NOT NULL,
    sender_id BIGINT UNSIGNED NOT NULL,
    body TEXT NOT NULL,
    read_at DATETIME NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (conversation_id) REFERENCES conversations(id) ON DELETE CASCADE,
    FOREIGN KEY (sender_id) REFERENCES users(id)
);

Later tables

Add listing_images, likes, saved_listings, comments, reviews, notifications, reports, and blocked_users after the core workflow is stable.

6. Secure Signup and Login

Use server-side validation for every request. Never trust validation performed only by Android or browser JavaScript.

$passwordHash = password_hash($password, PASSWORD_DEFAULT);

$stmt = $pdo->prepare(
    'INSERT INTO users (username, email, password_hash, campus)
     VALUES (?, ?, ?, ?)'
);
$stmt->execute([$username, strtolower($email), $passwordHash, $campus]);

During login, find the user by email or username and verify the password with password_verify(). Never send the password or password hash back to either client.

7. .education Email Verification

  1. Accept only the required institutional email format on the server.
  2. Create the account with is_verified = false.
  3. Generate a random, single-use verification token.
  4. Store only a hash of the token and an expiry time.
  5. Send a verification link to the student email.
  6. Set is_verified = true when the link is used.
  7. Restrict posting and messaging until verification is complete.

8. Connecting the Website

const response = await fetch('/api/auth/login.php', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ identifier, password })
});

const result = await response.json();
if (result.success) {
  localStorage.setItem('accessToken', result.accessToken);
}

Replace the current direct users.json logic in login.php and signup.php with database queries through PDO.

9. Connecting Android

Add Retrofit, its JSON converter, and OkHttp to the app module. Define API request and response classes, then replace authentication and post creation in DatabaseHelper with API calls.

public interface CampusConnectApi {
    @POST("auth/login.php")
    Call<LoginResponse> login(@Body LoginRequest request);

    @GET("listings/list.php")
    Call<List<Listing>> getListings(@Query("campus") String campus);

    @POST("listings/create.php")
    Call<Listing> createListing(@Body CreateListingRequest request);

    @POST("messages/send.php")
    Call<Message> sendMessage(@Body SendMessageRequest request);
}

Store tokens using secure Android storage backed by the Android Keystore. Keep local SQLite or Room for cached listings and offline UI, not for authoritative user accounts.

10. Migration Plan

  1. Create the MySQL database and tables.
  2. Update PHP signup and login to use PDO and password hashes.
  3. Import existing users.json users and require password resets because their old passwords are plaintext.
  4. Build and test the authentication endpoints with the website first.
  5. Add Retrofit to Android and connect Android login/signup.
  6. Move Android posts to the listings API.
  7. Add listing-based conversations and messages.
  8. Remove production dependence on users.json.

11. Security Requirements

  • Use HTTPS in production.
  • Use prepared SQL statements everywhere.
  • Hash passwords with password_hash().
  • Validate authorization on every protected endpoint.
  • Rate-limit login, signup, verification, and messaging.
  • Validate and safely resize uploaded images.
  • Implement report, block, and moderation actions.
  • Never log passwords, tokens, or private message bodies.

12. Recommended Implementation Order

  1. Database connection and users table.
  2. Signup, login, and verification API.
  3. Shared website authentication.
  4. Android Retrofit authentication.
  5. Listings API and feed synchronization.
  6. Listing-based messaging.
  7. Likes, saves, comments, reviews, and notifications.
